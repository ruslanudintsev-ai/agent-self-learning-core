# AGENTS.md — правила для AI-агентов в Agent Self-Learning Core

Этот публичный репозиторий содержит **локальную библиотеку CLI/CLE**. Не путайте её с универсальным интерфейсом для GitHub, инфраструктуры, продакшена или секретов.

## Перед началом любой задачи

1. Прочитайте `README.md` и соответствующие инструкции в `.agents/rules/`. Для новых CLE-команд — `.agents/rules/cle-command-authoring.md`, для фиксации повторяемых ошибок — `.agents/rules/self-learning.md`.
2. Проверьте существующие Issues, открытые PR и актуальный `main`. Не создавайте повторную задачу или конкурирующий PR без необходимости.
3. Ограничьте изменения задачей, укажите ожидаемый результат и риски. Не изменяйте незатронутые части CLI или системные правила ради наведения «красоты».
4. Используйте отдельную тематическую ветку и **Draft PR** до завершения проверки. Не отправляйте коммиты напрямую в `main`.

## Выбор инструментов и границы CLE

- `python manage.py <command>` / `cle <command>` — интерфейс **к поддерживаемым локальным командам CLE**. Для GitHub, CI, чтения документации, тестов и иных внешних систем используйте их штатные разрешённые инструменты. Требование «одна точка входа» не заменяет проверки полномочий.
- При разработке повторно используемой CLE-функции соблюдайте `.agents/rules/cle-command-authoring.md`: `core/commands/`, корректный контракт команды, тесты, ограниченный JSON и документация. Не плодите случайные одноразовые скрипты там, где у проекта уже есть подходящая команда.
- **Исследовать исходники и писать необходимые изолированные тесты разрешено**, когда это нужно для ревью, диагностики, корректности и безопасности. Вывод `--json` не является доказательством правильности реализации.
- **`cle exec` исполняет произвольный Python с правами вызывающего пользователя.** Timeout, режим `--dry-run` и Target Host Guard не являются полноценной песочницей или границей авторизации. Запрещено выполнять недоверенный код, обходить ограничения, открывать секреты и использовать этот механизм как общий удалённый executor.
- Разделяйте Dev и Production. Любые изменения production, права/секреты, системные службы, платные API, массовые операции, удаление веток и перенос данных требуют отдельного явного разрешения владельца.

## Проверки и отчётность

- Для изменений Python/CLE используйте штатные проверки, например `python -m pytest tests -q`; для новой команды дополнительно выполняйте её локальный `--help`, `--json` и `dev-validate` согласно инструкции разработки. Записывайте **точный SHA, фактически выполненную команду и exit code**.
- Успех одной команды не означает успешный CI, релиз или деплой. Если проверка не запускалась, указывайте `NOT_RUN`; если доказательства недоступны — `UNKNOWN`. Не объявляйте `PASS` по одному сообщению агента.
- В PR пишите: цель/Issue, какие файлы изменены, проверка на SHA, риски, влияние на совместимость и что осталось неизвестным. Не публикуйте токены, данные пользователей и приватные журналы.
- Merge, изменение `main`, публикация и удаление веток — только после требуемого явного согласования; никакого force-push общей истории.

**Для контрибьюторов:** [CONTRIBUTING.md](CONTRIBUTING.md). Эти корневые правила дополняют инструкции CLE; при конфликте действий не ослабляйте ограничения безопасности — зафиксируйте противоречие для владельца.
